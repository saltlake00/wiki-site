# 링 스택 게임 (Ring Stack)

> **판단**: 좌우 왕복을 **회전**으로 바꾼 이유는 하나다 — 실패가 쌓여도 실루엣이 망가지지 않게. 핵심은 **판정과 실루엣의 분리**(안은 이빨이 깎이고, 겉은 항상 같은 두께의 원기둥)다. Unity MCP 바이브 코딩 학습용 모작이고, 컨셉은 직접 고안이 아니다(출처 미확인).
> **다음**: 없음 — 기능은 완성 상태. 27층 입력 잠김 버그 내역은 회수해 아래 "알려진 버그와 수정"에 기록했다(원인 미특정, 방어 수정만).

스택(Stack) 장르의 핵심 재미(타이밍 탭 + 정렬 판정)를 유지하면서, 실패가 쌓여도
"피라미드"가 아닌 "일정 두께의 원기둥"으로 보이도록 재구성한 Unity 게임 프로젝트.

## 개요

- **컨셉**: 좌우 왕복 대신 **회전**으로 바꾼 스택 게임. 톱니(기어) 모양 도넛 링이 타워 축 기준으로 층마다 시계↔반시계 교대 회전.
- **핵심 트릭**: 판정과 실루엣을 분리 — 안에서는 이빨이 깎이지만, 겉에서 보면 항상 같은 두께의 원기둥.
- **목적**: Unity MCP를 활용한 바이브 코딩(vibe coding) 학습용 모작 프로젝트.
- **크레딧**: 컨셉은 직접 고안이 아니라 Reddit/YouTube에서 본 작업물을 따라 만든 것. 출처 미확인.

## 기술 스택

- Unity 6000.3.21f1 / URP (Universal Render Pipeline)
- 새 Input System (마우스/터치 통합)
- 커스텀 HLSL 셰이더 (Toon/NPR, 반투명 Unlit)
- 절차적 메시 생성 (별도 모델링 툴 없음)

## 핵심 메커니즘

- **판정**: 원둘레를 720개 각도 슬롯으로 표현, 겹침을 AND 연산으로 계산 → [[링스택-판정로직]]
- **메시**: 이웃 각도 분할과 정점을 공유하는 진짜 쐐기(부채꼴) 지오메트리 → [[링스택-절차적-메시]]
- **셰이더**: 명암을 뚜렷한 단계로 나누는 카툰풍 NPR 셰이더 → [[링스택-셰이더]]
- **색상**: OKLCH 기반 층별 그라데이션 → [[링스택-색상-팔레트]]
- **카메라**: 아이소메트릭(오소그래픽) 시점, 게임오버 시 줌아웃/오빗 리빌 → [[링스택-카메라]]

## 프로젝트 구조

```
Assets/Scripts/GearRingStack/
├── RingSlotUtil.cs           # 720슬롯 판정 로직
├── GearRingMeshBuilder.cs    # 슬롯 패턴 → 3D 메시
├── WheelCapBuilder.cs        # 우주정거장풍 덮개 메시
├── OklchColor.cs             # OKLCH → RGB 변환
├── FallingRing.cs            # 낙하 링 회전 + 탭 시점
├── TowerManager.cs           # 층 판정/누적, 난이도, 게임오버
├── GameManager.cs            # 입력, 상태 전이, 콤보
├── CameraRig.cs              # 아이소메트릭 카메라 + 리빌
├── UI/                       # HUD, 게임오버, 시작 화면, 탭 캐처
└── Editor/GearRingStackSceneBuilder.cs  # 씬 자동 생성 툴
```

## 알려진 버그와 수정

### 27층 입력 잠김 (2026-08-14 — 완화 완료, **원인 미특정**)

- **증상**: 실제 플레이 중 27층에서 탭이 안 먹어 더 진행이 안 됨. 재현 조건은 "특정 층수"로만
  보였고, 이후 같은 층에서 재현되지는 않았다.
- **조사**: Unity MCP로 **사용자가 실제 플레이 중인 라이브 세션**(마침 `CurrentLayer == 27`)에
  그대로 접속해 점검. `activeRing`·`basePattern`·`accumulatedRotation`·`GameManager.state`가
  **전부 정상**이었고, `TowerManager.TryDrop()`을 코드로 직접 부르면 즉시 28층으로 넘어갔다.
  → **판정 로직과 상태 전이는 건강했다.** 문제는 **탭이 게임까지 전달되는 경로**.
- **원인**: **특정하지 못했다.** 추정만 남아 있다 — 원시 입력 폴링(`Mouse`/`Touchscreen`)이
  특정 상황(포커스 상실, 입력 이벤트 누락)에서 탭을 놓친 것으로 보인다.
  (당시 "10~16층마다 주기적 리셋"과 엮인 것 아닌가 의심했지만, 리셋 로직은 정상 동작했다)
- **수정 (원인 제거가 아니라 방어)** — 커밋 `a1c2620`:
  1. `Touchscreen.current.touches` **전체 슬롯 순회**로 확대 (단일 터치만 보던 것)
  2. 화면 전체를 덮는 투명 UI `UI/TapCatcher.cs`(`IPointerDownHandler`) → `GameManager.OnTap()`.
     EventSystem 경로를 **이중화**해 폴링이 놓친 탭도 받는다

**이 방어 수정이 낳은 회귀 2건 — 재발 시 여기부터 본다:**

| 회귀 | 원인 | 수정 |
|---|---|---|
| 탭 한 번에 **2층**씩 쌓임 | 두 입력 경로가 같은 탭을 각각 처리 | `GameManager.OnTap()`에 `lastTapHandledFrame == Time.frameCount` 가드 — 프레임당 1회 (커밋 `9c48583`) |
| **가이드 버튼**을 눌러도 게임이 드롭됨 | 원시 폴링은 누른 위치를 안 봐서 UI 위 클릭도 탭으로 처리 | `IsPointerOverInteractiveUI()` — TapCatcher 외의 UI가 눌린 위치에 있으면 무시 (커밋 `7356205`) |

**재발 시 확인 순서** (`GameManager.cs` → `UI/TapCatcher.cs`):
`Update()`의 `WasTapPressedThisFrame` → `IsPointerOverInteractiveUI` 오탐 →
`OnTap()`의 프레임 가드 → TapCatcher가 EventSystem에 살아 있는지 → 마지막으로
[[링스택-판정로직|판정 로직]]의 `TryDrop`. **입력 경로가 2개라는 걸 잊지 말 것** —
회귀 2건 다 "경로가 둘"에서 나왔다.

> 교훈: 원인을 못 찾은 채 넣은 **방어적 이중화는 그 자체가 새 버그의 원천**이 됐다.
> 다음에 같은 증상이 보이면 방어를 더 얹기 전에 재현 로그(층수·입력 이벤트)를 먼저 남긴다.

## 실행 방법

1. Unity Hub에서 프로젝트 열기 (Unity 6000.3.21f1, URP)
2. 메뉴 `Tools > Gear Ring Stack > Build Scene` 실행 → 씬 자동 생성
3. Play 버튼 → 탭(마우스/터치)으로 회전 링 멈춰 쌓기
